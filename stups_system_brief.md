# Stups: System Brief

*Prepared for an external reviewer with no prior knowledge of the system.*

## What the system does

Stups is a personal recommendation agent that runs once a day without user input. At 17:30 each afternoon, an automated schedule triggers a workflow that retrieves the current Hamburg weather and a list of events happening in the city that evening. This information, together with a fixed written description of the user's preferences, is passed to a large language model, which selects two options and writes them as a short message. The message is delivered to the user's phone via Telegram.

The user does nothing except read it. There is no interface, no list to browse, and no request. The system decides and sends. The user cannot accept, reject, or correct a suggestion. There is no feedback channel back into the system, and nothing is recorded about whether the advice was followed.

## Inputs

Four categories of input enter the system.

| Input | Source | Personal data? |
|---|---|---|
| Live weather (temperature, sky condition) | OpenWeatherMap API | No |
| Dated event listings | Ticketmaster Discovery API | No |
| Event and cinema listings | Four scraped websites (hamburg.com, Stadtpark Open Air, Filmraum, Abaton, Kinopolis) | No |
| Taste profile (fixed text) | Written by the developer, stored in the model's system message | Yes |
| Telegram chat ID | Developer's own Telegram account | Yes |

The taste profile and the Telegram chat ID both constitute personal data about a single identifiable individual, the developer. The taste profile is transmitted to a third party model provider on every run.

## Outputs

The system produces free text generated by an external language model and delivers it directly to the user without any review, validation, or safety check. Present impact is limited because the sole recipient is the developer and the suggestions are non binding leisure activities.

Failure alerting exists through a separate Telegram notification workflow. This fires when a run fails technically. It does not review the content of a successful run. Technical monitoring exists; substantive oversight does not.

## Who is affected

One person: the developer, who is simultaneously the sole user and the only data subject. No third party receives output and no third party is profiled.

The suggestions touch no consequential domain. Not employment, credit, education, health, nor access to any service.

## Human review before action

None. No confirmation step exists between the model's output and delivery to the phone. The user reads the message after it has already been sent.

## Who built it

The developer configured the n8n workflow, wrote the taste profile, and authored the prompt.

The reasoning component is third party. DeepSeek and OpenAI supply the large language model. n8n supplies the runtime and scheduler. Six external sources supply the data.

The developer does not control the model's reasoning, but does control its instructions, and those instructions demonstrably change the output. A documented format defect, in which the two suggestions were chained into a single itinerary, was corrected by rewriting the prompt rather than by changing the model.

## Who would use it in production

Nobody uses the system in production. It is unpublished and single instance, with credentials held privately and a placeholder chat ID in the exported file.

A multi user version with stored preferences and mood tracking is documented in the go to market plan but has not been built.

## Why it was built

Stups was built as a personal proof of concept and submitted as a bootcamp course project.
